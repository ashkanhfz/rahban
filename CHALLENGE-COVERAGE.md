# Challenge coverage and limits

This document maps the Liara challenge to Rahban's implemented behavior. It describes capabilities, not a claim that every API is available to every account or that every flow has been demonstrated against a live account. Automated provider fixtures and Practice mode must be labeled as such.

| Challenge area | What Rahban does | Limit or user action |
|---|---|---|
| Initial setup | Inspects public GitHub/ZIP source; detects Dockerfile or Node.js, port, start configuration, and likely required JavaScript/TypeScript environment variables. | No arbitrary stack inference or execution of uploaded code on Rahban. Required values need a separate approved environment update or manual Liara setup. Private repositories and attached-disk deployments are unsupported. |
| Plan and app creation | Lists available plans with CPU/RAM/disk and returned bundle features, suggests a starter, displays rounded resource/bundle/total cost, selects a private network, and creates an app after approval. | Suggested size is a heuristic, not measured capacity. Account funding and creation of a missing private network remain in Liara. Existing-plan changes are not automated. |
| First and later deployments | Pins a source archive, fixes runtime settings, asks for exact-name approval, uploads/releases through Liara, checks release status and three consecutive HTTP successes. | A successful health route does not prove every application feature works. Unknown release results require investigation; they are not blindly retried. |
| Failure recovery | Restores editable drafts for eligible failed operations, creates a fresh proposal, and supports later verification of known releases. | A retry draft performs no cloud write. Ambiguous creates/releases require checking Liara before repeating them. |
| Diagnosis | Collects HTTP, logs, state, and optional resource evidence independently; ranks hypotheses with evidence and next steps. Optional model advice requires evidence-sharing consent. | Local rules and model advice are hypotheses. Missing API evidence is disclosed. The model cannot execute operations. The user chooses any configuration fix or approved restart. |
| Service management | Reads environment names; prepares add/update/remove patches without exposing existing values; supports approved start, stop, restart, and permanent app deletion. | Environment updates restart the app. Pending values are memory-only and must be re-entered after restart/expiry. App deletion may delete attached data; separate resources are not deleted. Stop is not a guarantee that all charges cease. Stop/delete pause health schedules and GitHub updates. |
| Monitoring | On-demand resource/health checks and optional 1/5/15/60-minute checks produce incidents and activity while Rahban is online and connected to the matching account. | CPU/RAM summary units are undocumented; raw samples do not establish saturation. No external alert delivery, external uptime guarantee, or automatic repair. Missed checks are not replayed. |
| Domain setup | Gives Liara/DNS/registrar steps, including IRNIC where applicable; reads domain/SSL/CNAME results and checks existing records through Liara. | The user adds domains, copies ownership/SSL records, edits DNS/nameservers, and enables SSL in the appropriate panels. No registrar credentials or DNS writes. |
| GitHub updates | Optional branch checks prepare pinned proposals for review. Optional exact-name standing authorization enables automatic deployment with the saved target and runtime settings. | Requires a previously verified public GitHub deployment. Restart, authorization changes, failed/uncertain deployment, or rejected/expired approval pauses updates. Re-enabling is explicit; no automatic rollback or retry of ambiguous writes. |
| Human control and UX | Deployments home, a three-step wizard, separate checks/settings, cost review, masked keys, retained error drafts, compact activity, local-history removal, and downloadable incident reports. | Single operator. Hiding a history entry does not delete an app or audit evidence. Local rules work without a model; external evidence sharing is optional. |
