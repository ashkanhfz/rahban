# Security and access

- Access is local by default. Public hosting requires an exact HTTPS `PUBLIC_ORIGIN` and an operator password hash. Login uses scrypt, attempt limits, and an eight-hour session with Secure, HttpOnly, and SameSite cookies.
- The API validates Host and Origin. Mutations require a session and CSRF token. Manual cloud operations require single-use approval of the exact target name, bound to the reviewed source, account, destination, and operation settings. The separately enabled automatic GitHub mode uses limited standing authorization as described below.
- Keys entered in the UI stay in server memory. `.env`, `data/`, and `hosting.private.json` are excluded from Git and the Docker build context. Private deployment packages contain a password hash. Do not publish `data/cloud-access.*`.
- The Liara API destination is fixed, and credentialed requests do not follow redirects. Reports redact known secret patterns; this does not guarantee removal of every sensitive value.
- User archives are neither executed nor extracted to disk. Suspicious paths, symlinks, and oversized input are rejected. Review source files for secrets before publication.
- GitHub source downloads are pinned to a commit SHA so branch updates cannot change the source being reviewed. Review mode requires a new approval for each prepared update. Automatic mode requires entering the exact app name to authorize future commits from the deployed repository and branch with fixed runtime settings. It uses the same source checks and deployment path, pauses after restart or failed/uncertain execution, and requires explicit re-enabling. It does not authorize app creation, plan changes, or repairs.
- Scheduled health checks are read-only and account-bound. They do not call the model or restart services. Resource units that the provider does not document remain unknown. Domain checks validate that the requested domain belongs to the selected app; Rahban does not write registrar or DNS settings.
- Environment edits expose current names only. Values for a proposed patch stay in server memory until use or expiry; stored proposals contain names and fingerprints. Execution rechecks the original environment before replacing it. Restart discards pending values. The editor clears typed values on preparation or close; stored environment-edit approvals and history do not contain them.
- Start, stop, environment updates, and app deletion require the same exact-name approval as other cloud changes. App deletion is irreversible and may remove attached data. Removing an operation from local history only hides an eligible terminal entry and preserves audit/approval evidence; it never deletes the Liara app.
- The model has no execution tools. Evidence sharing requires explicit consent. The model key and infrastructure token serve separate purposes.
- HTTP checks target the local sandbox or a derived `liara.run` hostname. Redirects are not followed. `/healthz` exposes application health and runtime identity metadata, never connection keys. The persistent `rahban:<instanceId>` signature and changing boot ID are attribution and restart indicators, not credentials or cryptographic identity proofs.
- Reconnection renews the local API session after a restart; it does not bypass public operator login or restore in-memory provider keys. Interrupted operations are not replayed automatically.
- Audit entries form a hash chain. Someone able to rewrite the whole database could also rewrite that chain. Restrict access to the data file and backups.

This is a single-operator MVP. Multi-user secret management, SSO, organizational RBAC, and independent backups are not implemented. Inspect the destination after an interrupted operation; Rahban does not blindly repeat cloud mutations.
